## 2. DATA MODEL – NEW TABLES (DRIZZLE)

Create the following Drizzle tables, using our existing conventions (naming, timestamp helpers, relations, etc.). Put them in the same schema file where other app tables live.

### `shopping_collections`

Represents user-defined collections (e.g. “Fall Outfits”, “Gifts”, “Wishlist”).

Fields:

- `id` – primary key (UUID or serial, match current style)
- `user_id` – references users table (use the same foreign key pattern as other user-owned entities)
- `name` – string (e.g. “Fall Capsule Wardrobe”)
- `description` – optional text
- `created_at`
- `updated_at`

### `shopping_items`

Represents a single saved product.

Fields:

- `id` – primary key
- `user_id` – references users table
- `collection_id` – nullable FK to `shopping_collections.id`  
  (for MVP: one collection per item; we can add many-to-many later)
- `title` – string
- `image_url` – string
- `canonical_url` – string (original product URL)
- `affiliate_url` – string, nullable (if we map through an affiliate system)
- `store` – string (e.g. “Zara”, “ASOS”) – can be derived from domain
- `price_current` – numeric/decimal (match our existing money representation)
- `price_last` – numeric/decimal, nullable (last known price)
- `currency` – string (e.g. “USD”) – default if needed
- `tags` – array of strings (use the same array type pattern we already use)
- `created_at`
- `updated_at`

### `shopping_price_snapshots`

Lightweight price history, one row per snapshot.

Fields:

- `id` – primary key
- `item_id` – FK -> `shopping_items.id`
- `price` – numeric/decimal
- `currency` – string
- `snapshot_at` – timestamp

Add proper indexes (e.g. `user_id` on items, `item_id` on snapshots) following the style of existing tables.

Generate and run migrations according to the repo’s usual Drizzle workflow.

## 3. BACKEND – SHOPPING APIS

Implement a small REST API surface under `/api/shopping/*` that:

All routes must:
- Authenticate the user using the same helper we use elsewhere (e.g. `getCurrentUser`, Supabase auth, etc.).
- Enforce per-tier limits (see section 4) before writing data.

### 3.1 `POST /api/shopping/add`

Use for **both**:
- “Paste URL → scrape product”
- “Save from Outfit Generator result card (with known data)”

Body (union style, handle both):

- Either:
  - `mode: "url"`
  - `url: string` – product URL to scrape

- Or:
  - `mode: "direct"`
  - `title: string`
  - `image_url: string`
  - `canonical_url: string`
  - `affiliate_url?: string`
  - `store?: string`
  - `price_current?: number`
  - `currency?: string`
  - `collection_id?: string`
  - `tags?: string[]`

Behavior:

- Verify user is logged in.
- Check **tier limits** (see section 4).
- If `mode: "url"`:
  - Fetch the page server-side.
  - Implement a **minimal scraper**:
    - Title: `og:title`, `<title>`, etc.
    - Image: `og:image` or main product image meta.
    - Price: attempt to extract from common selectors or meta tags. Be resilient, but MVP is fine: best-effort; if no price found, allow nullable with explicit flag in response.
    - Store: derive from the domain (e.g. `new URL(url).hostname` → cleaned).
  - Leave `affiliate_url` null for now (but keep the column in place).

- If `mode: "direct"`, trust the payload, but still require `canonical_url` minimally.

- Insert a new row into `shopping_items`.
- Insert a new `shopping_price_snapshots` entry if a price is present.
- Return the created item (with id, derived store, etc.).

### 3.2 `GET /api/shopping/list`

Query params:
- Optional `collection_id`
- Optional search/filter (e.g. `q` for title, `tag`)

Behavior:
- Return all items for the current user, filtered by collection if provided.
- Include a basic computed structure for the frontend:
  - per-store subtotal
  - global item count

### 3.3 `POST /api/shopping/collections/create`

Body:
- `name: string`
- `description?: string`

Behavior:
- Enforce collection limits based on tier.
- Create a new collection linked to current user.
- Return the new collection.

### 3.4 `POST /api/shopping/update`

Body:
- `id: string`
- Optional fields to update: `title`, `tags`, `collection_id`, etc.
- If price changes manually, also create a `shopping_price_snapshots` row.

### 3.5 `POST /api/shopping/delete`

Body:
- `id: string`

Behavior:
- Delete the item for this user (and optionally cascade snapshots).

### 3.6 `GET /api/shopping/price-history?item_id=...`

Return:
- Chronological list of snapshots for that `item_id`.
- Include `price`, `currency`, `snapshot_at`.

Implement all APIs using the existing patterns for API routes (error handling, auth, responses).
