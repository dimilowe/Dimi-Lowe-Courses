Step 3 — Cart Session Identity (Anon + Logged-In Merge)
Implement a server-owned method to resolve the current cart session.
Rules:
If user is logged in → use user_id cart session (create if missing).
If user is anonymous → use anon_session_id stored in an httpOnly cookie.
If user logs in and they have an anon cart → merge anon cart items into user cart, then mark anon session as merged/abandoned.
Acceptance:
Anonymous user can add items and refresh the page and still see cart.
After login, cart persists and contains prior anon items.
Step 4 — API Routes (Minimal Set, Server-Owned Validation)
Create API endpoints in the repo’s standard /api/* structure. Use request limiting middleware if available.
Endpoints:
GET /api/cart
returns current session + items + totals
POST /api/cart/items
body: CartItemInput
server validates and normalizes
adds item to current cart session
PATCH /api/cart/items/:id
update quantity (>=1)
DELETE /api/cart/items/:id
remove item
POST /api/cart/checkout
creates Stripe Checkout Session for all items
stores checkout intent/session id on cart session (add fields if needed)
returns checkout URL
POST /api/cart/webhook (Stripe webhook)
verifies signature
on success: marks cart checked_out and calls fulfillment router
Constraints:
Price, totals, and checkout creation must be computed server-side.
Never trust client-provided cents amounts as authoritative beyond initial request; validate/normalize.
Acceptance:
You can add 2 items, checkout, and webhook marks session checked_out.
If webhook fails verification, do nothing.
Step 5 — Fulfillment Router (MVP)
Implement a fulfillment router that runs after successful payment.
MVP behavior:
For each cart item, write a fulfillment_events record (create table if needed) with:
cart_session_id
cart_item_id
status: fulfilled | failed
payload jsonb
For now, fulfillment is “record-only” (no external fanout required).
The router must be implemented as an engine-owned server module, not in the webhook file.
Constraints:
Keep it deterministic and idempotent (webhooks can retry).
If same checkout is processed twice, fulfillment should not duplicate.
Acceptance:
After checkout, fulfillment events exist for each item.
Retrying webhook does not double-create fulfillment.
