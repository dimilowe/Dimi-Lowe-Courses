Why it’s false
If MP4 “truncated at first NUL byte” were happening, your stored object size would typically be 0 bytes, not 1 byte, and your earlier “Array len=1” symptom wouldn’t match “string cut at NUL” anyway.
Also: you already proved the Object Storage client was returning an Array not a Buffer. That’s not a UTF-8 truncation problem — that’s “you didn’t store bytes as bytes” / “you stored the wrong type” / “SDK incompatibility with stream mode.”
Why base64 is a bad move here
+33% storage + bandwidth immediately.
Slower uploads, slower finalize, slower processing.
More memory pressure (you’ll decode big blobs).
More moving parts (text APIs, decoding, verification).
And you still might hit platform request limits depending on how you post the base64.
You were one step away from the correct solution: uploadFromBytes + downloadAsBytes with Buffer normalization, and then ensure input_key points to the assembled binary object.
