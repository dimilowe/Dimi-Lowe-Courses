The two things to sanity-check
1) “Registry is kept as a fallback for non-entitlements metadata”
That’s fine only if:
pages/listings pull metadata from DB or
the registry metadata is not used to determine what exists / what’s shown
If your tool discovery/listing is DB-backed (you said it is), then keeping registry metadata around is harmless. It becomes a legacy convenience layer.
If any UI is still rendering tool cards from registry while gating from DB, you can get a new drift class:
DB tool exists but registry doesn’t → tool disappears from some views
registry tool exists but DB doesn’t → phantom UI entries
So: registry is okay as a backup only if DB is the canonical “tool exists” source everywhere.
2) “Backfilled all 54 tools from the registry”
Good, but you must ensure new tools created in DB don’t require a registry entry for gating.
Since you’ve moved gating to DB, the registry should not be required for:
access control
tool existence in lists
tool page routing
If new tools still need registry entries for names/categories/etc, you’re still running a split-brain system. Not for entitlements anymore, but still for tool identity. That’s survivable, but not ideal.
The single best confirmation test
Ask Replit to run this:
Create a brand-new tool row only in DB (no registry entry)
Set required_tier='pro' + required_clouds=['video']
Confirm:
it appears in admin tools list
gating works (UpgradeWall / API 403)
no runtime errors due to missing registry metadata
If that passes, then yes: the migration is truly complete and DB is the SSoT.
One more required check: unique slugs
Make sure tools.slug is unique (or treated as unique). If it isn’t, gating by slug can behave unpredictably.
Verdict
Yes, this is correct provided:
all gating reads are DB-only (no registry entitlement fallback still lurking)
tool existence/listing is DB-canonical everywhere
registry is not required for new tools to function
