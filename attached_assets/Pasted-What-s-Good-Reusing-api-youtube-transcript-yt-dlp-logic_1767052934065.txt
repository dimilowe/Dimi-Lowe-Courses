Two Critical Fixes to the Plan
1) Don’t “reuse transcript fetching” inside ClipRadar unless necessary
You already have a transcript endpoint. Best architecture:
Step A: /api/youtube/transcript returns timestamped segments (upgrade it)
Step B: /api/tools/clip-radar/analyze accepts segments and returns results
That way:
transcript fetching stays one responsibility
ClipRadar works with uploaded VTT/SRT later without changing logic
you can reuse timestamped transcripts across future tools
If you bake fetching into ClipRadar, you’ll duplicate logic and reintroduce drift later.
2) Exports should be generated from results, not from transcript
Exports should be pure functions of the selected windows + metadata.
Keep export generation isolated so it doesn’t destabilize scoring.
The “Must-Haves” (Ship v1 with these)
If you do nothing else, do these and you’ll have a real tool.
A) Upgrade /api/youtube/transcript to return segments
Add a query param like format=segments:
default returns plain text (keeps backwards compatibility)
format=segments returns:
[
  { "start": 12.34, "end": 15.20, "text": "no way" },
  ...

This is the highest leverage change because it upgrades your whole platform.
B) ClipRadar Analyze API (deterministic)
Input: segments + options
Output: ranked windows + exports.
No LLM required to ship.
C) De-dup peaks
Without suppression, you’ll get 10 clips from the same 40 seconds.
Make suppression a first-class step.
D) “Why flagged” explanations
Users won’t trust the tool unless you show:
which signals triggered
why it ranked high
