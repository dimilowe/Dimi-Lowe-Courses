⚠️ What might not work (or could bite you later)
1. lib/pricing/shoppingLimits.ts as a separate SSoT
It’s fine, but be careful you’re not creating a second pricing truth.
Better approach:
Either extend existing CLOUD_ENTITLEMENTS with a shoppingLimits field per tier
Or have a single SHOPPING_CLOUD_LIMITS_BY_TIER exported from the same place you keep cloud pricing
You want one mental model:
“All cloud behavior & limits are defined in the cloud entitlements/pricing layer.”
If you introduce a totally separate pricing folder, you risk divergence later.
2. Custom engine vs. “standard tool grid”
You’re right that Shopping Cloud needs a different layout (collections sidebar + grid). Just be intentional about how you register it:
If CloudDashboardEngine expects an engine ID / config, add a shopping-cloud-dashboard engine entry in ENGINE_REGISTRY and treat it as type: 'cloud-dashboard' or similar.
Don’t hardcode Shopping Cloud as a random special route that bypasses the engine registry completely.
Reason: later, when you want to treat cloud dashboards as CMS objects or MBBs, you’ll be glad Shopping Cloud already fits the pattern.
3. Scraper complexity
Even with “minimal” scraping, watch for:
Timeouts
Weird CORS / non-HTML responses
Sites that render everything via JS (no useful meta tags)
MVP fallback rule:
If scrape fails → create the item with just canonical_url + store domain + “Unknown Product” title, and let the user edit title manually. Don’t block saving entirely.
🔁 Push it further (without adding chaos)
1. Shape the limits config cleanly
Instead of random numbers in code, define something like:
export const SHOPPING_CLOUD_LIMITS = {
  free: {
    maxItems: 20,
    maxCollections: 1,
  },
  basic: {
    maxItems: Infinity,
    maxCollections: Infinity,
  },
  pro: {
    maxItems: Infinity,
    maxCollections: Infinity,
  },
} as const;
Then in the API:
const tier = getUserTier(user);
const limits = SHOPPING_CLOUD_LIMITS[tier];

if (itemCount >= limits.maxItems) {
  return errorWithUpgradeHint('items', limits.maxItems, 'shopping-basic');
}
errorWithUpgradeHint can follow the same shape/keys your upgrade modal pattern already expects.
